# AWS Lambda

## Overview

The Engineering Company IT Lab uses AWS Lambda to process document
events generated by the S3 → SQS workflow.

The Lambda function runs locally in the Floci AWS-compatible
environment and demonstrates event-driven serverless processing.

The current function is:

    Name:
        document-processor

    Runtime:
        Python 3.12

    Handler:
        index.handler

The function is triggered by messages arriving in the
`document-processing` SQS queue.


## Lambda Role

The function uses an IAM execution role rather than an IAM user.

The execution role is:

    document-processor-role

The role is assumed by the Lambda service through:

    sts:AssumeRole

The trust relationship allows:

    Principal:
        lambda.amazonaws.com

    Action:
        sts:AssumeRole


## Lambda Permissions

The Lambda execution role has permissions required by the current
document-processing workflow.

These include:

### S3

The function can read objects from:

    engineering-documents

Permission:

    s3:GetObject

Resource:

    arn:aws:s3:::engineering-documents/*


### SQS

The function can consume messages from:

    document-processing

Permissions:

    sqs:ReceiveMessage
    sqs:DeleteMessage
    sqs:GetQueueAttributes

Resource:

    arn:aws:sqs:eu-east-1:000000000000:document-processing


### CloudWatch Logs

The Lambda role includes permissions required for Lambda logging:

    logs:CreateLogGroup
    logs:CreateLogStream
    logs:PutLogEvents


### Secrets Manager

The Lambda execution role also has permission to retrieve the
database credentials stored in:

    engineering/document-processor/database

Permission:

    secretsmanager:GetSecretValue

The permission is scoped to the corresponding secret resource.


## Event Source Mapping

Lambda is connected to SQS through an Event Source Mapping.

The relationship is:

    S3
        |
        | ObjectCreated
        v
    document-processing
    SQS
        |
        | Event Source Mapping
        v
    document-processor
    Lambda

The current event source mapping uses:

    Batch size:
        1

    State:
        Enabled

Lambda therefore receives SQS messages as invocation events.


## Function Input

The Lambda function expects an SQS event.

Each SQS message contains the S3 event notification generated when
an object is created.

The relevant structure is:

    SQS event
        |
        +-- Records[]
              |
              +-- body
                    |
                    +-- S3 event
                          |
                          +-- Records[]
                                |
                                +-- eventName
                                +-- eventTime
                                +-- s3
                                      |
                                      +-- bucket
                                      +-- object
                                            |
                                            +-- key
                                            +-- size
                                            +-- eTag


## Event Processing

The Lambda handler processes the incoming event in several steps.

### 1. Receive SQS event

Lambda receives the event generated by the SQS Event Source Mapping.

### 2. Parse the SQS message body

The message body is decoded from JSON.

### 3. Extract the S3 event

The nested S3 event notification is extracted from the SQS message.

### 4. Extract document metadata

The function extracts:

    bucket
    object_key
    event_type
    event_time
    etag
    size_bytes

### 5. Retrieve database credentials

The function retrieves the database secret from Secrets Manager.

The secret name is supplied through the Lambda environment:

    SECRET_NAME

### 6. Connect to PostgreSQL

The function uses the retrieved credentials to connect to the
PostgreSQL database.

### 7. Store document metadata

The extracted metadata is inserted into the:

    documents

table.

### 8. Complete processing

If processing succeeds, the Lambda invocation completes successfully.

The SQS message is then deleted by the Lambda/SQS integration.


## Database Integration

The Lambda function writes document metadata to the PostgreSQL
database:

    engineering-documents-db

The current database schema contains fields including:

    id
    bucket
    object_key
    event_type
    event_time
    etag
    size_bytes
    status
    uploaded_at
    processed_at
    error_message
    created_at
    updated_at

The uploaded document itself is not stored in PostgreSQL.

The document remains in S3 while PostgreSQL stores metadata about
the document and its processing state.


## Secrets Manager Integration

Database credentials are not hard-coded in the current Lambda
function.

The function retrieves the secret using:

    secretsmanager.GetSecretValue

The secret contains the PostgreSQL connection information required
by the Lambda function.

The general flow is:

    Lambda
        |
        | GetSecretValue
        v
    Secrets Manager
        |
        | database credentials
        v
    Lambda
        |
        | PostgreSQL connection
        v
    RDS PostgreSQL


## Logging

The Lambda function uses Python's `logging` module.

The current implementation records information about:

    function invocation
    received SQS events
    S3 event type
    bucket
    object key
    database record creation

Lambda execution logs are available through:

    /aws/lambda/document-processor

in the local CloudWatch Logs implementation.

Example workflow logging includes:

    document-processor invoked
    received SQS event
    document recorded

## Database Verification

Successful Lambda processing was verified by querying the
`documents` table directly.

Example:

    SELECT
        id,
        bucket,
        object_key,
        event_type,
        size_bytes,
        status,
        uploaded_at
    FROM documents
    ORDER BY id;


A successful test produced a document record containing the
corresponding S3 bucket and object key.


## Operational Notes

The Lambda function is intentionally implemented as a relatively
simple laboratory workload.

The current implementation focuses on demonstrating:

    Lambda execution
    IAM execution roles
    SQS event source mapping
    SQS event consumption
    S3 event extraction
    Secrets Manager integration
    PostgreSQL integration
    CloudWatch logging

Additional production-oriented improvements such as advanced
idempotency, structured error handling, and deliberate retry/DLQ
configuration are outside the current implementation scope.
