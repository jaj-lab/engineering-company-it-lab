## CLOUD INCIDENTS
## INC-001

Title:

```
Floci State Loss
```

Summary:

```
Floci resources were expected to persist across
container recreation, but application state was not
present in the initially expected /app/data location.
```

Investigation:

```
The Floci container used:

    /app/data

backed by:

    floci_data


The volume itself remained present.

However, the expected cloud resource state was not
available in the configured application data path.
```

Conclusion:

```
Docker named-volume persistence and application-level
state persistence are separate concerns.

A named volume only persists the data that the
application actually writes into that volume.
```

Operational lesson:

```
Do not assume that a named Docker volume guarantees
application-state persistence without verifying where
the application stores its state.
```

Document:

```
docs/incidents/INC-001-floci-state-loss.md
```

## INC-002

Title:

```
Floci Lambda Execution Failure
```

Summary:

```
Lambda invocation failed because Floci could not
communicate with the Docker daemon from inside
the Floci container.
```

Root cause:

```
Floci Lambda execution requires Docker access.

The Floci container did not have the Docker socket
mounted and accessible during the failed configuration.
```

Observed error:

```
java.net.SocketException:
No such file or directory
```

Investigation:

```
Floci attempted to access:

    unix:///var/run/docker.sock
```

Resolution:

```
Mount the host Docker socket into the Floci container:

    /var/run/docker.sock
        →
    /var/run/docker.sock
```

Verification:

```
[x] Docker socket visible inside Floci
[x] Lambda container successfully created
[x] Lambda container successfully started
[x] Lambda invocation successful
[x] SQS event source successfully invoked Lambda
```

Operational lesson:

```
A local cloud emulator that launches workload
containers requires access to the container runtime.
```

Document:

```
docs/incidents/INC-002-floci-lambda-exec-failure
```

## INC-003

Title:

```
Floci State Lost After Compose Integration
```

Summary:

```
Previously created Floci AWS resources appeared to
disappear after combining / restructuring the Docker
Compose configuration.
```

Initial symptom:

```
Floci started successfully, but previously created
cloud resources were no longer visible.
```

Investigation:

```
The investigation initially focused on Docker Compose
configuration and persistent storage behavior.

The previous Floci state was then compared with the
volumes available to the new Compose configuration.
```

Root cause:

```
The new Compose configuration was using / binding a
NEW Docker volume instead of reusing the EXISTING
volume that contained the previous Floci state.
```

Important distinction:

```
The original volume containing the previous state
had NOT been deleted.

The new Floci deployment was simply attached to a
different volume.
```

Actual situation:

```
OLD DEPLOYMENT
    |
    v
existing volume
    |
    +--> previous Floci state


NEW COMPOSE CONFIGURATION
    |
    v
new volume
    |
    +--> empty / new Floci state
```

Resolution:

```
Identify the original volume containing the previous
Floci state.

Reconfigure the Compose deployment to bind/reuse the
existing volume instead of creating a new one.
```

Result:

```
Previous Floci state became available again after
the correct volume was reused.
```

Operational lesson:

```
Docker Compose project changes can unintentionally
result in a different named volume being used.

Before concluding that persistent data was deleted,
verify:

    docker volume ls

    docker volume inspect <volume>

    Compose volume configuration

    Actual mount source


Persistent storage must be verified by both:

    volume identity

and:

    mount configuration.
```

Key lesson:

```
"The volume exists" does not necessarily mean
"the current container is using that volume."
```

Document:


## INC-004

Title:

```
SMB Share Access Configuration Issue
```

Summary:

```
An SMB share permission configuration did not match
the intended access behavior during testing.
```

Context:

```
The SMB shares were initially created with restricted
read-only access.

User / group access testing exposed the mismatch between
the configured share permissions and the intended
resource-access model.
```

Investigation:

```
Share-level permissions were inspected and compared
against the intended group-based access model.
```

Resolution:

```
The affected SMB share permissions were corrected
during incident resolution.

The final implementation was verified against the
intended share and NTFS permission model.
```

Result:

```
SMB access behavior matched the implemented
group-based permissions.
```

Operational lesson:

```
SMB access is determined by the combination of:

    User
        |
        v
    Security Group
        |
        v
    SMB Share Permissions
        +
    NTFS Permissions
        |
        v
    Resource Access


Share permissions and NTFS permissions must both be
considered when troubleshooting Windows file access.
```
