# Amazon RDS

## Overview

The Engineering Company IT Lab uses PostgreSQL through the AWS-compatible
RDS service provided by Floci.

The database stores metadata generated by the document-processing
workflow.

The current database instance is:

    Identifier:
        engineering-documents-db

    Engine:
        PostgreSQL

    Database:
        documents

    Master username:
        engineering


## Purpose

RDS is used as the persistent metadata store for the document
processing workflow.

The uploaded documents themselves remain in S3.

PostgreSQL stores information extracted from S3 events, including:

    bucket
    object_key
    event_type
    event_time
    etag
    size_bytes
    processing status
    timestamps
    error information


## Architecture

The database is part of the following workflow:

    S3
        |
        | ObjectCreated

    SQS
        |
        | SQS event
        v
    Lambda
    document-processor
        |
        | INSERT document metadata
        v

    engineering-documents-db
        |
        v
    documents

## Database Connectivity

The local Floci environment exposes the PostgreSQL service through
its container network.

The database was verified using PostgreSQL client tools.

Connectivity was tested with:

    nc -vz <database-address> 7001

The database can then be accessed using `psql`.

Example:

    PGPASSWORD='password' psql \
      -h <database-address> \
      -p 7001 \
      -U engineering \
      -d documents


The database address is part of the local Floci environment and is
not a public AWS RDS endpoint.


## Database Schema

The current database contains a single primary table:

    documents


The schema is:

    documents
    |
    +-- id
    +-- bucket
    +-- object_key
    +-- event_type
    +-- event_time
    +-- etag
    +-- size_bytes
    +-- status
    +-- uploaded_at
    +-- processed_at
    +-- error_message
    +-- created_at
    +-- updated_at


### Columns

`id`

    BIGSERIAL PRIMARY KEY

Unique identifier for each stored document event.

`bucket`

    VARCHAR(63) NOT NULL

Name of the S3 bucket containing the object.

`object_key`

    TEXT NOT NULL

S3 object key identifying the uploaded object.

`event_type`

    VARCHAR(100) NOT NULL

S3 event type that triggered processing.

`event_time`

    TIMESTAMPTZ NOT NULL

Timestamp supplied by the S3 event.

`etag`

    VARCHAR(128)

Object ETag when provided by the event.

`size_bytes`

    BIGINT

Object size reported by the S3 event.

`status`

    VARCHAR(32) NOT NULL DEFAULT 'received'

Current processing state of the document.

`uploaded_at`

    TIMESTAMPTZ NOT NULL DEFAULT NOW()

Timestamp associated with the document record.

`processed_at`

    TIMESTAMPTZ

Timestamp for completed processing when applicable.

`error_message`

    TEXT

Field reserved for processing error information.

`created_at`

    TIMESTAMPTZ NOT NULL DEFAULT NOW()

Record creation timestamp.

`updated_at`

    TIMESTAMPTZ NOT NULL DEFAULT NOW()

Record update timestamp.


## Indexes

## Lambda Integration

The `document-processor` Lambda function connects to PostgreSQL
after receiving an S3 event through SQS.

The processing flow is:

    S3 event
        |
        v
    SQS message
        |
        v
    Lambda
        |
        +-- parse event
        |
        +-- extract metadata
        |
        +-- retrieve DB credentials
        |
        +-- connect to PostgreSQL
        |
        +-- INSERT into documents
        |
        v
    RDS


For each S3 event, Lambda extracts the document metadata and inserts
a corresponding row into the `documents` table.


## Database Credentials

Database credentials are stored in AWS Secrets Manager.

The Lambda function retrieves the credentials at runtime instead of
storing the database password directly in the function code.

The secret used by the workflow is:

    engineering/document-processor/database


The secret provides the connection information required by Lambda:

    host
    port
    dbname
    username
    password


The relationship is:

    Lambda
        |
        | GetSecretValue
        v
    Secrets Manager
        |
        | credentials
        v
    Lambda
        |
        | PostgreSQL connection
        v
    RDS


## Document Processing State

The `status` field provides a simple representation of document
processing state.

The initial record is created with:

    status = 'received'


Additional state handling can be introduced later as the application
workflow is expanded.

## Scope

The current RDS implementation is intentionally simple and is intended
for the local cloud laboratory.

The database currently provides:

    PostgreSQL persistence
    document metadata storage
    basic processing state
    Lambda integration
    direct verification through psql

Production-oriented database concerns such as high availability,
automated backups, replication, migrations, connection pooling, and
advanced recovery procedures are outside the current laboratory scope.
