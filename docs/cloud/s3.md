# S3

## Overview

Amazon S3 is used in the Engineering Company IT Lab as the object
storage layer for the document-processing workflow.

The local S3-compatible service is provided by Floci.

The current implementation contains one primary bucket:

    engineering-documents

The bucket stores uploaded document objects.

S3 is also the starting point of the event-driven processing workflow:

    S3
        |
        | ObjectCreated
        v
    SQS
        |
        v
    Lambda
        |
        v
    RDS PostgreSQL

## Bucket

### engineering-documents

The `engineering-documents` bucket is the primary document storage
location for the cloud workflow.

The bucket contains objects uploaded by the laboratory application
layer and by direct testing through the AWS CLI.

The current implementation uses object keys such as:

    incoming/test-document.txt

    incoming/lambda-processing-test.txt

    incoming/lambda-rds-test.txt

    incoming/secrets-test.txt


The bucket can be listed with:

    aws s3 ls


The bucket can also be inspected through the S3 API:

    aws s3api list-buckets


## Object Operations

The S3 implementation was verified using direct object operations.


### List Objects

Objects in the bucket can be listed with:

    aws s3api list-objects \
      --bucket engineering-documents


### Upload Object

An object can be uploaded with:

    aws s3api put-object \
      --bucket engineering-documents \
      --key files/test-document.txt \
      --body tmp/test-document.txt


The same operation was used to generate test events for the document
processing workflow.


### Download Object

Objects can be downloaded with:

    aws s3api get-object \
      --bucket engineering-documents \
      --key files/test-document.txt \
      tmp/downloaded-document.txt


These operations verify that objects can be stored and retrieved from
the local S3-compatible environment.


## IAM Integration

Access to the bucket is controlled through IAM policies.

The `engineering-app` IAM user is associated with the
`engineering-app-s3` policy.

The intended permissions are:

    s3:ListBucket
    s3:GetObject
    s3:PutObject

The bucket-level permission applies to:

    arn:aws:s3:::engineering-documents

Object-level permissions apply to:

    arn:aws:s3:::engineering-documents/*


The Lambda execution role also has permission to read objects from
the bucket:

    s3:GetObject

Resource:

    arn:aws:s3:::engineering-documents/*


The IAM implementation and the observed Floci authorization
limitation are documented in:

    docs/cloud/iam.md


## Event Notification

The `engineering-documents` bucket is integrated with the
`document-processing` SQS queue.

When an object is created in the bucket, S3 produces an object-created
event.

The event is delivered to SQS for asynchronous processing.

The current workflow is:

    PutObject
        |
        v
    engineering-documents
        |
        | ObjectCreated:Put
        v
    document-processing
        |
        v
    document-processor


The event contains information about the created object, including:

- bucket name
- object key
- event type
- event time
- ETag
- object size


## S3 → SQS Integration

The S3 event is wrapped inside the SQS message body.

The resulting structure is conceptually:

    SQS message
        |
        +-- body
             |
             +-- S3 event
                  |
                  +-- eventName
                  +-- eventTime
                  +-- s3
                       |
                       +-- bucket
                       |    |
                       |    +-- name
                       |
                       +-- object
                            |
                            +-- key
                            +-- size
                            +-- eTag


The Lambda function parses this structure after receiving the SQS
message.


## Document Processing Workflow

S3 acts as the entry point for document processing.

The current workflow is:

    1. An object is created in `engineering-documents`.

    2. S3 generates an ObjectCreated event.

    3. The event is delivered to `document-processing`.

    4. Lambda receives the SQS message through its Event Source
       Mapping.

    5. Lambda extracts the S3 event information.

    6. Lambda stores document metadata in PostgreSQL.

    7. Successful Lambda execution results in the SQS message being
       deleted.


The document itself remains stored in S3.

Only its metadata is stored in the PostgreSQL `documents` table.


## Verification

The S3 workflow was verified by uploading test objects.

Example:

    echo "Lambda RDS integration test" > tmp/lambda-rds-test.txt

    aws s3api put-object \
      --bucket engineering-documents \
      --key incoming/lambda-rds-test.txt \
      --body tmp/lambda-rds-test.txt


The resulting workflow was observed as:

    S3 PutObject
        |
        v
    engineering-documents
        |
        | ObjectCreated:Put
        v
    document-processing
        |
        | message received
        v
    document-processor
        |
        +-- S3 event parsed
        +-- bucket extracted
        +-- object key extracted
        +-- metadata stored
        |
        v
    Lambda succeeded
        |
        v
    SQS message deleted


The workflow was subsequently verified with the database by querying
the `documents` table for the inserted object metadata.


## Storage Model

S3 stores the actual document objects.

PostgreSQL stores metadata describing the objects and their processing
state.

The current storage model is therefore:

    S3
    |
    +-- document object
    |
    +-- document object
    |
    +-- document object


    RDS PostgreSQL
    |
    +-- bucket
    +-- object_key
    +-- event_type
    +-- event_time
    +-- etag
    +-- size_bytes
    +-- status
    +-- processing metadata


This separation keeps object storage and document metadata in their
respective services.
